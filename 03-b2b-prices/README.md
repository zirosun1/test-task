# Задание 03: диагностика цены B2B

## Запуск

Из этой папки:

```sh
php run.php <client_id> <sku> [qty]
php tests.php
```

`tests.php` использует временный файл кеша и не меняет приложенный `var/cache.json`.

## Что проверяет tests.php

Это небольшой самостоятельный PHP-скрипт, для которого не нужны PHPUnit или другие библиотеки. Он загружает `PriceResolver.php`, читает прайсы и правила из CSV/JSON, а затем проверяет расчёты при фиксированном времени **22.10.2026, 12:00, Минск**. Фиксированное время нужно, чтобы результат не менялся при повторном запуске в другой день.

Функция `same()` сравнивает ожидаемое и фактическое значения. При совпадении печатает `OK`; при несовпадении останавливает проверку и сообщает ожидаемое и фактическое значения.

Проверяются девять условий:

1. Для K-003 и B-105 отсутствует цена `DEALER`; код должен выдать понятную ошибку, а не подставить `RETAIL`.
2. Сентябрьская акция для K-001 и B-101 не действует 22 октября: скидка должна быть 0%.
3. Цена K-001 за B-101 без завершённой акции должна быть 14,75.
4. Для K-002 при покупке 12 штук B-106 должна примениться наибольшая скидка — 5%, а не сумма персональной, объёмной и акционной скидок.
5. Цена B-106 для этого заказа с учётом скидки 5% должна быть 3,51.
6. Старое значение кеша 15,48 для K-004 и B-103 не должно перекрыть новую цену OPT2 — 15,72.
7–8. Проверяются цены K-005 и K-006 на B-107 с активной октябрьской акцией: 10,89 для OPT1 и 10,28 для OPT2.
9. Акция действует включительно в последний день `valid_to`: для B-106 31 октября скидка составляет 4%.

Для шестого сценария тест создаёт отдельный временный кеш с устаревшим значением. После проверки временный файл удаляется, поэтому исходный `var/cache.json` остаётся без изменений. Первый сценарий напрямую проверяет метод `basePrice()` и наличие ошибки; он не проверяет формат вывода `run.php`.

Проверка выполнена командой `php tests.php`: все 9 сценариев завершились `OK`.

## Ошибки в коде и исправления

1. **Скидки складывались.** Исходный код прибавлял каждую подходящую скидку (`+=`). Я заменил это на выбор наибольшей скидки через `max()`. Например, для K-002 вместо 12% применяется 5%, цена B-106 — 3,51.
2. **Акции проверялись сравнением строк.** Даты формата `дд.мм.гггг` сравнивались как текст, поэтому сентябрьская акция ошибочно действовала 22 октября. Теперь даты разбираются и сравниваются как даты; последний день акции включён.
3. **Розничная цена подставлялась при отсутствии нужного типа.** Для K-003 у B-105 нет цены DEALER, но исходный код возвращал RETAIL. Теперь в такой ситуации выдаётся понятная ошибка, и неверная цена не показывается.
4. **Ключ кеша не учитывал изменения цены.** В нём были только клиент, товар и количество, поэтому после смены типа цены могла вернуться старая цена. Теперь ключ учитывает тип цены, базовую цену и скидку. Для K-004 актуальная цена OPT2 — 15,72; старое значение 15,48 больше не используется.

## Найденные причины и действия

1.   K-003 / B-105:   в `prices.csv` для B-105 нет строки `DEALER`. Исходный код незаметно подставлял RETAIL. Исправление: отсутствующий тип цены теперь считается ошибкой данных; синхронизировать/проверить выгрузку цен из 1С и не показывать клиенту цену другого типа.
2.   K-001 / B-101:   скидка 7% приходит из сентябрьской акции. Сравнение дат в исходнике было строковым: для формата `дд.мм.гггг` оно ошибочно считало её активной 22 октября. Исправление: даты разбираются и сравниваются как даты; скидка равна 0%, цена 14,75.
3.   K-002 / B-106 x12:   12% сложились из персональных 5%, объёмных 3% и октябрьской акции 4%. По правилу применяется максимум, поэтому скидка 5%, цена 3,51.
4.   K-004 / B-103:   цена 15,48 — старая запись в `var/cache.json`, сохранённая в 09:05. На 12:00 она ещё не истекла. По актуальным данным OPT2 цена 15,72. Исправление: версия ключа кеша учитывает текущий тип цены, базовую цену и скидку; новые расчёты не используют результат с прежними входными данными.
5.   K-005 и K-006 / B-107:   ошибки нет: OPT1 для K-005 даёт 11,34, OPT2 для K-006 — 10,71. Цена различается из-за разных типов цен клиентов.

## Как не допустить повторения

-   Кеш:   сбрасывать связанные цены при изменении типа цены клиента, прайса или правил; включать версию/подпись входных данных в ключ и задавать TTL соразмерно частоте обновления. После обновления прайса проверять контрольные цены.
-   Отсутствующая цена:   при импорте валидировать обязательные сочетания SKU и типов цен, вести отчёт об отсутствующих строках и не подменять цену другого типа. До устранения расхождения не подтверждать цену заказа автоматически.

## Принятые решения

- Персональная скидка, объёмная скидка и акция считаются подходящими кандидатами; применяется только наибольший процент.
- Конец акции включён в период её действия.
- Неизвестную цену не заменяем розничной: явная ошибка предотвращает выдачу неверной цены.
